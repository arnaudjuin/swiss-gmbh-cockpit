    01The architecture decision

    The repo has two frontends over one FastAPI backend. The classic SPA (static/js/01–09) renders template strings into hidden <div class="page"> elements. cockpit-next/ replaces that layer with Next.js 15 + React 19 + TypeScript, without touching the backend.

    This is the single most important thing to understand: here, Next.js is used as a frontend framework with a build server, not as a full-stack framework. There are no API routes, no server actions, no database access from Node. All domain logic — Swiss payroll, VAT, the payable-date rule, the forecast — stays in Python, where it has 173 tests. If you have ever put an Angular app in front of a Spring or .NET API, you already know this shape.

    The bridge is one rewrite rule:

    cockpit-next/next.config.mjs — complete file

    /** @type {import('next').NextConfig} */
const API = process.env.API_URL || "http://127.0.0.1:8000";

// The FastAPI backend stays the single source of truth. In dev (and behind a
// single reverse proxy in prod) every /api call is forwarded there, so the
// browser talks same-origin and the Bearer token flows through untouched.
const nextConfig = {
  async rewrites() {
    return [{ source: "/api/:path*", destination: `${API}/api/:path*` }];
  },
};

export default nextConfig;

    Every browser call to /api/… is proxied server-side to FastAPI. Same origin, so no CORS, and the auth header travels untouched. This is exactly Angular's proxy.conf.json — except it also runs in production, and it is resolved at build time (lesson 14 tells that war story).

    Why two frontends at once is not madness

    Both frontends read and write the same server-side state: the SQLite DB through the same endpoints, and the same /preferences document for UI state (widget layouts, forecast inputs, settings). Nothing lives only in a browser. That single decision is what makes an incremental port safe: any page can be used from either frontend on any day, and they cannot disagree. When you plan a migration at work — AngularJS→Angular, Angular→React, monolith frontend→micro-frontends — this is the property to engineer first.

    02React in one lesson, for Angular hands

    Angular separates a component into a class (state + logic), a template (its own language: *ngIf, *ngFor, pipes, bindings) and DI-provided collaborators. React collapses all three into one construct: a function that returns its UI.

    function Meter({ pct, mod }: { pct: number; mod?: "ok" | "warn" | "danger" }) {
  return (
    <div className="meter">
      <div className={`meter__bar${mod ? ` meter__bar--${mod}` : ""}`}
           style={{ width: `${Math.min(100, Math.max(0, pct))}%` }} />
    </div>
  );
}

    Read this as: the component is the template, and the template is plain TypeScript. The consequences replace half of Angular's template language:

    • *ngIf → a boolean expression: {error && <div>…</div>}, or a ternary, or an early return from the function (this project uses early returns for loading/error states — a pattern Angular templates cannot express).
    • *ngFor → {rows.map(r => <tr key={r.id}>…</tr>)}. The key is your trackBy, except mandatory in spirit: without it React diffs list children by position and re-mounts on reorder.
    • Pipes → function calls: {chf(m.income)}. No registration, no purity rules; it's just an import.
    • Attribute bindings → props: className= (not class), style takes an object, onChange/onClick take functions.

    The rendering model, in three sentences

    When state changes, React re-runs the whole component function, gets a new element tree, diffs it against the previous one, and patches the real DOM minimally. Angular instead keeps your class instance alive and re-evaluates template bindings when zone.js signals that something async happened. So: Angular = long-lived instance + automatic dirty checking; React = re-executed function + explicit state setters. Nothing re-renders unless you call a setter.

    Because the function re-runs, anything computed inline is automatically fresh — the project's pages derive filtered lists as plain consts on every render (lesson 8) where Angular would reach for pipes or memoized selectors. At this app's scale that's free; useMemo exists for when it isn't.

    The habit to unlearn

    In Angular you mutate: this.rows.push(x), and change detection finds it. In React state is replaced, never mutated: setRows([...rows, x]), setBiz({ ...biz, iban: v }). Every state update in this repo is a spread for exactly that reason — a mutated object is reference-equal, so React (and its diffing) treats it as unchanged.

    The App Router's convention: a folder under app/ is a URL segment; the page.tsx inside it is the component for that URL. This project's entire "router config" is the directory listing:

    app/page.tsx — the whole file

    redirect() in a server component runs during rendering — the Angular equivalent of a default route { path: '', redirectTo: 'dashboard' }, but expressed as code, and it happens on the server before any JS ships.

    The layout is your persistent shell

    layout.tsx renders once and persists across navigations — the sidebar does not re-mount when you move from Bills to Payroll, exactly like a component outside the router-outlet. The current page arrives as children:

    app/layout.tsx

  return (
    <html lang="en">
      <head><script dangerouslySetInnerHTML={{ __html: themeInit }} /></head>

    (That inline script applies the saved dark-mode class before first paint — the classic flash-of-wrong-theme fix; lesson 12.) Layouts nest: a folder can carry its own layout.tsx wrapping only its subtree, the analogue of a child route with its own shell component. This app needs only the root one.

    Navigation: three mechanisms, two used

    • <Link href> — client-side navigation with prefetching, the routerLink equivalent.
    • useRouter().push() — imperative navigation, used after login: router.push("/dashboard"). Your Router.navigate().
    • Plain <a href> — full page load. The Shell's sidebar deliberately uses these: every page fetches fresh on mount anyway, the app is 103 kB, and during the port some links pointed at the classic frontend on another origin, where Link can't help. A conscious trade of SPA-smoothness for simplicity — swapping them for Link later is a find-and-replace.

    05Rendering: server components, hydration, and what ○ Static means

    The App Router's headline feature: components are server components by default. They run only on the server (at build or request time), emit HTML, ship zero JS, and cannot use state, effects, or browser APIs. A file that needs interactivity declares "use client" on line one — and that directive marks a boundary: everything it imports becomes client code too.

    The timeline for a page in this app

    1. Build time — next build renders each page's static shell (the component tree up to the first data fetch: sidebar, headers, "Loading…" state) to HTML. That's the ○ (Static) in the build output.
    2. Request — the server returns that HTML instantly. First paint shows the full chrome with the loading hint. No white screen, no spinner-only page.
    3. Hydration — React attaches to the server HTML and the components become live. The Angular analogue is Universal + provideClientHydration(), except here it's the default, not an add-on.
    4. Data — useEffect fires, api() calls FastAPI through the rewrite, state fills, the page re-renders with numbers.

    Why this app is 95% client components

    • The auth token lives in localStorage (parity with the classic SPA against the same backend). Server components cannot read it, so they cannot fetch authenticated data on the user's behalf.
    • Everything on screen is live user data. There is nothing meaningful to render at build time beyond the shell — and the shell does prerender.
    • One mental model during a port. A client component behaves like an Angular component: mount → fetch → render → update. The port stayed mechanical because every page follows the same skeleton.
    The serialization rule at the boundary

    Props crossing from a server component into a "use client" component must be serializable — plain data, no functions, no class instances, no Date methods you rely on. This project's boundary is trivial (the root layout passes only children), but the rule is the #1 source of confusion in mixed apps; it is why "just pass a callback down" sometimes fails across the boundary.

    Hydration mismatches

    Server HTML and the client's first render must be identical, or React warns and patches. Classic trap: rendering new Date(), random values, or theme-dependent markup. This app sidesteps the theme case by setting data-theme in a <head> script before paint, and keeping theme out of React state entirely — CSS tokens react to the attribute, React never knows (lesson 12).

    If you rebuilt it server-first

    Move the token to an httpOnly cookie, make each page.tsx an async server component that awaits FastAPI directly (forwarding cookies()), and keep only the interactive leaves — search boxes, paid-toggles, the forecast cells — as small client islands. The CSS and the backend wouldn't change a line. That is exercise 3, and it's the highest-value one.

    app/login/page.tsx (core)

    FastAPI issues an opaque token held in an in-memory session table; the client stores it in localStorage and sends it as Authorization: Bearer. Route protection is data-level, not route-level: any 401 anywhere clears the token and hard-redirects to /login (lesson 7).     Check yourself

    Which attack does the localStorage token model NOT protect against?

    Bearer-from-localStorage is CSRF-immune but XSS-readable. httpOnly cookies flip the trade — and would enable server-side auth.

    Why do PDF links carry ?token=… instead of a header?

    A plain link can't send Authorization. The backend accepts a query token exactly for downloads.

    07The data layer — your HttpClient in 30 lines

    Angular gives you HttpClient (typed via generics) plus interceptors for auth and errors. Here the same three jobs are one function:

    lib/api.ts

    export class ApiError extends Error {
  constructor(public status: number, message: string) { super(message); }
}

export async function api<T = unknown>(path: string, opts: RequestInit = {}): Promise<T> {
  const token = typeof window !== "undefined" ? localStorage.getItem("session_token") : null;
  const res = await fetch(`/api${path}`, {
    ...opts,
    headers: {
      // FormData must set its own multipart boundary — don't force JSON on it
      ...(opts.body && !(opts.body instanceof FormData) ? { "Content-Type": "application/json" } : {}),
      ...(token ? { Authorization: `Bearer ${token}` } : {}),      // auth interceptor
      ...(opts.headers || {}),
    },
  });
  if (res.status === 401) {                                        // error interceptor
    localStorage.removeItem("session_token");
    window.location.href = "/login";
    throw new ApiError(401, "Not authenticated");
  }
  if (!res.ok) {
    let detail = res.statusText;
    try { detail = (await res.json()).detail ?? detail; } catch { /* keep statusText */ }
    throw new ApiError(res.status, String(detail));
  }
  return (res.headers.get("content-type") || "").includes("json") ? res.json() : (undefined as T);
}

    Worth pausing on each defensive line: the typeof window guard keeps the module importable during server rendering; the FormData branch exists because setting Content-Type manually on multipart bodies breaks the boundary parameter (a bug every framework's users rediscover); the detail dance surfaces FastAPI's error messages instead of "Unprocessable Entity".

    08State, effects, refs — the four hooks actually used

    The whole app is built from four hooks. Master these against their Angular counterparts and you have read every page.

    useState — the field and the change detector

    const [all, setAll] = useState<Obligation[] | null>(null);

    null doubles as the loading flag — the early-return pattern replaces both *ngIf="loading" and skeleton templates:

    if (error) return <div className="notice notice--danger">{error}</div>;
if (!all)  return <div className="hint">Loading…</div>;

    Two forms of setter: setAll(rows) replaces; setV(x => x + 1) (the functional form, used by the chart theme hook) reads the current value — required whenever the update depends on previous state, because the closed-over variable may be stale.

    useEffect — ngOnInit and ngOnDestroy in one

    useEffect(() => {
  const bump = () => setV(x => x + 1);
  window.addEventListener("themechange", bump);
  return () => window.removeEventListener("themechange", bump);   // ← ngOnDestroy
}, []);   // [] = run once on mount = ngOnInit

    The dependency array is the contract Angular never asks you to write: it lists every reactive value the effect reads. [] means "on mount". A wrong array is the React equivalent of a subscription leak — which is why the pages wrap their loaders in useCallback:

    const reload = useCallback(() => {
  api<Obligation[]>("/obligations").then(setAll).catch(e => setError(String(e)));
}, []);                       // stable identity across re-renders
useEffect(reload, [reload]);  // satisfies the lint contract, runs once

    Why the ceremony: a function declared inline is a new function on every render; as an effect dependency it would re-fire the effect each time. useCallback pins its identity — think of it as promoting a template lambda to a bound class method. The Obligations page also calls reload() after a paid-toggle, the same refetch-after-mutate you'd write in a service.

    useRef — the instance field that must not re-render

    The Bills search debounce, complete:

    2 · Uncontrolled + key (server-recomputed cells)

    The Forecast's per-month income cells would fight a controlled binding: the user types, the server recomputes, the cell must then show server truth. The escape hatch:

    app/forecast/page.tsx

    <input type="number" defaultValue={Math.round(m.income)} key={`${m.key}-${m.income}`}
       onBlur={e => { if (Number(e.target.value) !== Math.round(m.income))
                        setMonthIncome(m.key, e.target.value); }} />

    defaultValue makes it uncontrolled (the DOM owns the text while typing); changing the key after a save re-mounts the input with fresh server data. Commit on blur, not on every keystroke. File the trick: "uncontrolled with reset key" solves every editable-cell-against-computed-data case.

    3 · Validation where it's cheap

    function localeValid(l: string) { try { (0).toLocaleString(l); return true; } catch { return false; } }

    The Forecast income cells use defaultValue plus a changing key. Why?

    'Uncontrolled with reset key' is the pattern for editable cells the server recomputes — a controlled binding would fight the user mid-typing.

    11Shared services without DI

    providedIn: 'root' gives Angular a lazy singleton. In React-land a plain module already is one — ES imports are cached, so module-level state is app-wide state:

    lib/prefs.ts

    let cache: Record<string, unknown> | null = null;    // the singleton's private field

export async function loadPrefs(): Promise<Record<string, unknown>> {
  if (!cache) cache = await api<Record<string, unknown>>("/preferences");
  return cache;
}

export function pref<T>(prefs: Record<string, unknown>, path: string, fallback: T): T {
  let cur: unknown = prefs;
  for (const key of path.split(".")) {
    if (cur == null || typeof cur !== "object") return fallback;
    cur = (cur as Record<string, unknown>)[key];
  }
  return (cur === undefined ? fallback : cur) as T;
}

export async function setPref(path: string, value: unknown): Promise<void> {
  const prefs = await loadPrefs();
  // walk/create the path, set the leaf…
  await api("/preferences", { method: "PUT", body: JSON.stringify(prefs) });
}

    The important design choice is where the real state lives: on the server. The same /preferences document drives the classic SPA's widgets, the forecast's per-month income entries, the Settings page, even the dividend-tax parameters. That's why a number typed in the old frontend appears in the new one — and why there is no Redux, no NgRx-equivalent, no client store at all. When state must be shared, this app shares it through the API.

    12Styling: one CSS file, two frontends

    Angular scopes styles per component (ViewEncapsulation); Next offers CSS Modules for the same job — and this project deliberately uses neither. app/app.css is a copy of the classic frontend's stylesheet: one global file built on design tokens, with BEM-ish class names supplying the discipline that encapsulation would otherwise enforce.

    Why: the two frontends had to be pixel-identical during the port, and the design system predates it. React components are thin wrappers over canonical classes (lesson 10), so a designer's change lands in both frontends. The cost is stated in the code's own comment: the file is copied, not imported (Next won't bundle CSS from outside its root), so changes must be mirrored — a documented trade, not an accident.

    Theming without React

    Dark mode is a data-theme attribute plus token redefinition. React is kept out of it almost entirely:

    app/layout.tsx — before first paint, no flash

    const themeInit = `
try { if (localStorage.getItem('theme') === 'dark') document.documentElement.dataset.theme = 'dark'; } catch {}
`;
<head><script dangerouslySetInnerHTML={{ __html: themeInit }} /></head>

    components/Shell.tsx — the toggle

    const toggleTheme = () => {
  const next = document.documentElement.dataset.theme === "dark" ? "light" : "dark";
  document.documentElement.dataset.theme = next;
  localStorage.setItem("theme", next);
  window.dispatchEvent(new Event("themechange"));   // only the charts care (lesson 13)
};

    CSS custom properties respond to the attribute; components reference tokens; nothing re-renders except the charts, which must repaint canvas pixels. Compare with the Angular habit of a ThemeService + observable + async pipes — the platform (CSS) was already the reactive system needed.

    Display settings flow through one module

    lib/money.ts holds the currency label and locale as module state, set once from preferences in the Shell; every chf() call in every page then formats accordingly. Change "CHF · de-CH" to "EUR · en-US" in Settings and the entire app — cards, tables, chart ticks — re-formats. One module, no injection token, no pipe re-registration.

    A stated trade: pixel parity between frontends beats DRY here; the copy must be mirrored manually and the code says so.

    13Charts and the registration gotcha

    Chart.js is wrapped by react-chartjs-2 the way ng2-charts wraps it for Angular. Chart.js v4 is tree-shakeable, which means you register every piece you use — scales, elements, plugins, and controllers:

    components/charts.tsx

    ChartJS.register(CategoryScale, LinearScale, BarElement, LineElement, PointElement,
  Tooltip, Legend, ArcElement, BarController, LineController);
                       // ↑ the two everyone forgets
    Gotcha we actually hit

    The first build compiled clean and crashed at runtime with Error: "bar" is not a registered controller. Elements and scales are not enough — mixed-type charts (type: "bar" dataset + type: "line" overlay, which both money charts use) also need their controllers registered. TypeScript cannot catch it; only opening the page can. Budget one E2E smoke per chart-bearing page.

    Theme-reactive canvas

    Canvas pixels don't respond to CSS variables, so the chart components read tokens at render time and subscribe to the toggle's event:

    function vizToken(name: string) {           // lib/money.ts
  return getComputedStyle(document.documentElement).getPropertyValue(name).trim();
}

function useThemeVersion() {                // components/charts.tsx
  const [v, setV] = useState(0);
  useEffect(() => {
    const bump = () => setV(x => x + 1);
    window.addEventListener("themechange", bump);
    return () => window.removeEventListener("themechange", bump);
  }, []);
  return v;
}

    Bumping a counter nobody reads is the idiomatic "force re-render on external event" — on the next render vizToken("--viz-income") returns the other theme's value and the dataset colors rebuild. The design system stays the single source of truth for color; the charts just ask.

    Also note what the chart config doesn't do: no dual axes (income, outflow and running cash share one CHF scale), tooltips formatted through the same chf() as the tables, and category colors pinned to semantic tokens — the data-viz rules from the design system, enforced by shared helpers rather than review comments.

    The env-var trap that cost a debugging loop

    rewrites() is executed during next build and the result is baked into the routes manifest. Setting API_URL when running next start does nothing — the freshly started server kept proxying to the old backend while the login kept failing with the right password. Identical mental model to environment.ts: build-time, not runtime. The Docker build therefore takes it as a build ARG; changing backends means rebuilding the image (or fronting both with one reverse proxy and never baking a URL at all).

    CI as a type gate

    The GitHub workflow runs two jobs: backend (seed + 173 smoke tests) and frontend (npm ci && next build). The build type-checks every page — so when the backend job's API shape and a frontend interface drift apart, the compile fails before any frontend test exists. Cheap insurance; the same role ng build plays in an Nx monorepo pipeline.

    15Performance: what actually ships, what would be next

    • First paint is prerendered HTML — chrome and loading state — then one request per data source. The classic SPA, by contrast, ships a blank shell and builds everything in JS; the port's first paint is objectively better without anyone optimizing.
    • Bundle discipline comes from the route table: any PR that balloons a page shows up as a number in the build output. The one heavy route (dashboard, +71 kB) is heavy for a reason — three canvases.
    • Re-render hygiene is structural rather than tuned: state lives in the page that uses it, so typing in the Bills search re-renders the Bills page, not the shell. No OnPush-style annotations exist because nothing global re-renders in the first place.

    The honest next steps, in order of value: swap sidebar <a> for Link (kills full-page reloads between pages), next/dynamic the chart components (moves Chart.js out of the dashboard's first load), and SWR for cache-and-revalidate navigation (data appears instantly from cache, refreshes behind). Each is an hour, none was needed to ship.

    Check yourself

    Why doesn't the app need OnPush-style render tuning?

    Re-render hygiene is structural: no global state → no global re-renders. Optimization starts only when the build-table numbers say so.
