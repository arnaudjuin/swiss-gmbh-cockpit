    01The architecture decision — a story in two acts

    This repo's history is the course's best teaching material, because it made a decision most migrations get wrong, then used it to pull off something bigger than planned.

    Act I — Next.js as a frontend with a build server

    The app began as one FastAPI backend with a vanilla-JS SPA (template strings rendered into hidden <div class="page"> elements — static/js/01–09). cockpit-next/ first replaced only that layer: Next.js 15 + React 19 + TypeScript, without touching the backend. No API routes, no database access from Node. All domain logic — Swiss payroll, VAT, the payable-date rule — stayed in Python, where it had 173 tests. If you have ever put an Angular app in front of a Spring or .NET API, you know this shape.

    The bridge was one rewrite rule, and its final form is worth reading closely:

    cockpit-next/next.config.mjs — complete file (final form)

    /** @type {import('next').NextConfig} */
const API = process.env.API_URL || "http://127.0.0.1:8000";

const nextConfig = {
  async rewrites() {
    // FALLBACK phase: Next's own route handlers (including dynamic ones
    // like /api/reports/pl/[year]) win; only endpoints not yet ported fall
    // through to FastAPI. afterFiles would shadow dynamic routes.
    return { fallback: [{ source: "/api/:path*", destination: `${API}/api/:path*` }] };
  },
};

export default nextConfig;

    Every browser call to /api/… that Next cannot answer itself is proxied server-side to FastAPI. Same origin, so no CORS; the Bearer token travels untouched. It is Angular's proxy.conf.json — except it also runs in production, and the phase (fallback, not afterFiles) is what lets Next routes take over one at a time. Lesson 16 tells the war story behind that comment.

    Act II — the strangler fig eats the backend

    Because the proxy loses to any route handler Next defines, the backend could be ported endpoint by endpoint: write app/api/obligations/route.ts, and FastAPI silently stops receiving /api/obligations — while 170 other endpoints keep working through the proxy. Each tranche was verified against the Python original with a parity harness (lesson 20) before the next began. Today all 176 endpoints serve from Node — payroll engine, CAMT.053 bank parsing, pdfkit invoices, exceljs exports, accountant ZIPs, the AI chat — the schema self-installs on an empty SQLite file, and FastAPI remains in the repo purely as the reference implementation the port is tested against. This pattern has a name — the strangler fig — and this codebase is a complete, inspectable example of it.

    Why two implementations at once was not madness

    Both frontends — and during the port, both backends — read and write the same server-side state: one SQLite file, one /preferences document for UI state. Nothing lives only in a browser or only in one process's memory. That single property is what made incremental migration safe: any page could be served by either stack on any day, and they could not disagree. When you plan a migration at work — AngularJS→Angular, monolith→micro-frontends, Python→TypeScript — this is the property to engineer first.

    Map to Angular

    Act I is proxy.conf.json promoted to production. Act II has no Angular equivalent — it is what becomes possible when the framework in front of your API is itself a Node server: the proxy target and the replacement code live in one process, so the migration boundary moves one file at a time.

    Check yourself

    Why must the /api proxy live in the fallback rewrite phase rather than afterFiles?

    afterFiles rewrites are checked after static files but before dynamic route matching — a dynamic route handler would never be reached. fallback runs only when nothing else matched, which is exactly the strangler-fig contract.

    What single property made the endpoint-by-endpoint backend port safe?

    Shared server-side state (one DB, one preferences document) means either stack can serve any request on any day. The parity harness then proves the answers are identical.

    02React in one lesson, for Angular hands

    Angular separates a component into a class (state + logic), a template (its own language: *ngIf, *ngFor, pipes, bindings) and DI-provided collaborators. React collapses all three into one construct: a function that returns its UI.

    function Meter({ pct, mod }: { pct: number; mod?: "ok" | "warn" | "danger" }) {
  return (
    <div className="meter">
      <div className={`meter__bar${mod ? ` meter__bar--${mod}` : ""}`}
           style={{ width: `${Math.min(100, Math.max(0, pct))}%` }} />
    </div>
  );
}

    Read this as: the component is the template, and the template is plain TypeScript. The consequences replace half of Angular's template language:

    • *ngIf → a boolean expression: {error && <div>…</div>}, or a ternary, or an early return from the function (this project uses early returns for loading/error states — a pattern Angular templates cannot express).
    • *ngFor → {rows.map(r => <tr key={r.id}>…</tr>)}. The key is your trackBy, except mandatory in spirit: without it React diffs list children by position and re-mounts on reorder.
    • Pipes → function calls: {chf(m.income)}. No registration, no purity rules; it's just an import.
    • Attribute bindings → props: className= (not class), style takes an object, onChange/onClick take functions.

    The rendering model, in three sentences

    When state changes, React re-runs the whole component function, gets a new element tree, diffs it against the previous one, and patches the real DOM minimally. Angular instead keeps your class instance alive and re-evaluates template bindings when zone.js signals that something async happened. So: Angular = long-lived instance + automatic dirty checking; React = re-executed function + explicit state setters. Nothing re-renders unless you call a setter.

    Because the function re-runs, anything computed inline is automatically fresh — the project's pages derive filtered lists as plain consts on every render (lesson 8) where Angular would reach for pipes or memoized selectors. At this app's scale that's free; useMemo exists for when it isn't.

    The habit to unlearn

    In Angular you mutate: this.rows.push(x), and change detection finds it. In React state is replaced, never mutated: setRows([...rows, x]), setBiz({ ...biz, iban: v }). Every state update in this repo is a spread for exactly that reason — a mutated object is reference-equal, so React (and its diffing) treats it as unchanged.

    The App Router's convention: a folder under app/ is a URL segment; the page.tsx inside it is the component for that URL. This project's entire "router config" is the directory listing:

    app/

    app/page.tsx — the whole file

    import { redirect } from "next/navigation";
export default function Home() { redirect("/dashboard"); }

    redirect() in a server component runs during rendering — the Angular equivalent of a default route { path: '', redirectTo: 'dashboard' }, but expressed as code, and it happens on the server before any JS ships.

    The layout is your persistent shell

    layout.tsx renders once and persists across navigations — the sidebar does not re-mount when you move from Bills to Payroll, exactly like a component outside the router-outlet. The current page arrives as children:

    app/layout.tsx

    export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <head><script dangerouslySetInnerHTML={{ __html: themeInit }} /></head>
      <body><Shell>{children}</Shell></body>
    </html>
  );
}

    (That inline script applies the saved dark-mode class before first paint — the classic flash-of-wrong-theme fix; lesson 12.) Layouts nest: a folder can carry its own layout.tsx wrapping only its subtree, the analogue of a child route with its own shell component. This app needs only the root one.

    Navigation: three mechanisms, two used

    • <Link href> — client-side navigation with prefetching, the routerLink equivalent.
    • useRouter().push() — imperative navigation, used after login: router.push("/dashboard"). Your Router.navigate().
    • Plain <a href> — full page load. The Shell's sidebar deliberately uses these: every page fetches fresh on mount anyway, the app is 103 kB, and during the port some links pointed at the classic frontend on another origin, where Link can't help. A conscious trade of SPA-smoothness for simplicity — swapping them for Link later is a find-and-replace.

    05Rendering: server components, hydration, and what ○ Static means

    The App Router's headline feature: components are server components by default. They run only on the server (at build or request time), emit HTML, ship zero JS, and cannot use state, effects, or browser APIs. A file that needs interactivity declares "use client" on line one — and that directive marks a boundary: everything it imports becomes client code too.

    The timeline for a page in this app

    1. Build time — next build renders each page's static shell (the component tree up to the first data fetch: sidebar, headers, "Loading…" state) to HTML. That's the ○ (Static) in the build output.
    2. Request — the server returns that HTML instantly. First paint shows the full chrome with the loading hint. No white screen, no spinner-only page.
    3. Hydration — React attaches to the server HTML and the components become live. The Angular analogue is Universal + provideClientHydration(), except here it's the default, not an add-on.
    4. Data — useEffect fires, api() calls FastAPI through the rewrite, state fills, the page re-renders with numbers.

    Why this app is 95% client components

    • The auth token lives in localStorage (parity with the classic SPA against the same backend). Server components cannot read it, so they cannot fetch authenticated data on the user's behalf.
    • Everything on screen is live user data. There is nothing meaningful to render at build time beyond the shell — and the shell does prerender.
    • One mental model during a port. A client component behaves like an Angular component: mount → fetch → render → update. The port stayed mechanical because every page follows the same skeleton.
    The serialization rule at the boundary

    Props crossing from a server component into a "use client" component must be serializable — plain data, no functions, no class instances, no Date methods you rely on. This project's boundary is trivial (the root layout passes only children), but the rule is the #1 source of confusion in mixed apps; it is why "just pass a callback down" sometimes fails across the boundary.

    Hydration mismatches

    Server HTML and the client's first render must be identical, or React warns and patches. Classic trap: rendering new Date(), random values, or theme-dependent markup. This app sidesteps the theme case by setting data-theme in a <head> script before paint, and keeping theme out of React state entirely — CSS tokens react to the attribute, React never knows (lesson 12).

    If you rebuilt it server-first

    Move the token to an httpOnly cookie, make each page.tsx an async server component that awaits FastAPI directly (forwarding cookies()), and keep only the interactive leaves — search boxes, paid-toggles, the forecast cells — as small client islands. The CSS and the backend wouldn't change a line. That is exercise 3, and it's the highest-value one.

    06Auth: the login flow and its trade-offs

    2026 update

    Everything below still holds — the auth contract (Bearer header, session cookie, ?token=) is unchanged. What changed is who verifies it: the TypeScript backend now does, and sessions live in a SQLite table (ts_sessions) rather than process memory. Lesson 17 explains the production bug that forced that move.

    app/login/page.tsx (core)

  e.preventDefault();

    FastAPI issues an opaque token held in an in-memory session table; the client stores it in localStorage and sends it as Authorization: Bearer. Route protection is data-level, not route-level: any 401 anywhere clears the token and hard-redirects to /login (lesson 7). Coarser than CanActivate, and honest about what is actually being protected — the data, not the empty page shell.

    Which attack does the localStorage token model NOT protect against?

    07The data layer — your HttpClient in 30 lines

    Angular gives you HttpClient (typed via generics) plus interceptors for auth and errors. Here the same three jobs are one function:

    lib/api.ts

    export class ApiError extends Error {
  constructor(public status: number, message: string) { super(message); }
}

export async function api<T = unknown>(path: string, opts: RequestInit = {}): Promise<T> {
  const token = typeof window !== "undefined" ? localStorage.getItem("session_token") : null;
  const res = await fetch(`/api${path}`, {
    ...opts,
    headers: {
      // FormData must set its own multipart boundary — don't force JSON on it
      ...(opts.body && !(opts.body instanceof FormData) ? { "Content-Type": "application/json" } : {}),
      ...(token ? { Authorization: `Bearer ${token}` } : {}),      // auth interceptor
      ...(opts.headers || {}),
    },
  });
  if (res.status === 401) {                                        // error interceptor
    localStorage.removeItem("session_token");
    window.location.href = "/login";
    throw new ApiError(401, "Not authenticated");
  }
  if (!res.ok) {
    let detail = res.statusText;
    try { detail = (await res.json()).detail ?? detail; } catch { /* keep statusText */ }
    throw new ApiError(res.status, String(detail));
  }
  return (res.headers.get("content-type") || "").includes("json") ? res.json() : (undefined as T);
}

    Worth pausing on each defensive line: the typeof window guard keeps the module importable during server rendering; the FormData branch exists because setting Content-Type manually on multipart bodies breaks the boundary parameter (a bug every framework's users rediscover); the detail dance surfaces FastAPI's error messages instead of "Unprocessable Entity".

    08State, effects, refs — the four hooks actually used

    The whole app is built from four hooks. Master these against their Angular counterparts and you have read every page.

    useState — the field and the change detector

    const [all, setAll] = useState<Obligation[] | null>(null);

    null doubles as the loading flag — the early-return pattern replaces both *ngIf="loading" and skeleton templates:

    if (error) return <div className="notice notice--danger">{error}</div>;
if (!all)  return <div className="hint">Loading…</div>;

    Two forms of setter: setAll(rows) replaces; setV(x => x + 1) (the functional form, used by the chart theme hook) reads the current value — required whenever the update depends on previous state, because the closed-over variable may be stale.

    useEffect — ngOnInit and ngOnDestroy in one

    useEffect(() => {
  const bump = () => setV(x => x + 1);
  window.addEventListener("themechange", bump);
  return () => window.removeEventListener("themechange", bump);   // ← ngOnDestroy
}, []);   // [] = run once on mount = ngOnInit

    The dependency array is the contract Angular never asks you to write: it lists every reactive value the effect reads. [] means "on mount". A wrong array is the React equivalent of a subscription leak — which is why the pages wrap their loaders in useCallback:

    const reload = useCallback(() => {
  api<Obligation[]>("/obligations").then(setAll).catch(e => setError(String(e)));
}, []);                       // stable identity across re-renders
useEffect(reload, [reload]);  // satisfies the lint contract, runs once

    Why the ceremony: a function declared inline is a new function on every render; as an effect dependency it would re-fire the effect each time. useCallback pins its identity — think of it as promoting a template lambda to a bound class method. The Obligations page also calls reload() after a paid-toggle, the same refetch-after-mutate you'd write in a service.

    useRef — the instance field that must not re-render

    • First paint is prerendered HTML — chrome and loading state — then one request per data source. The classic SPA, by contrast, ships a blank shell and builds everything in JS; the port's first paint is objectively better without anyone optimizing.

      cockpit-next/server/http.ts — complete auth + error contract

      export const json = (data: unknown, status = 200) => NextResponse.json(data, { status });

// Same auth contract as FastAPI: Bearer header, session cookie, or ?token=.
export function requireAuth(req: NextRequest): NextResponse | null {
  const h = req.headers.get("authorization") || "";
  const bearer = h.startsWith("Bearer ") ? h.slice(7) : null;
  const cookie = req.cookies.get("session")?.value ?? null;
  const query = req.nextUrl.searchParams.get("token");
  if (validToken(bearer) || validToken(cookie) || validToken(query)) return null;
  return err(401, "Not authenticated");
}

export function guard(handler) {
  return async (req: NextRequest, ctx: any) => {
    const unauthorized = requireAuth(req);
    if (unauthorized) return unauthorized;
    try { return await handler(req, ctx); }
    catch (e) { return err(500, e instanceof Error ? e.message : "Internal error"); }
  };
}
      Note err() produces {"detail": …} — FastAPI's error shape, preserved so no frontend code had to change.

    • ctx.params is a Promise since Next 15. Every handler starts with const { id } = await ctx.params; — forget the await and TypeScript saves you, which is more than Python did.

    The most surprising choice first: the TypeScript backend talks to SQLite synchronously, via better-sqlite3. No await, no pool, no ORM:

    if (!tableExists(_db, "invoices")) {          // fresh file? install the schema
      for (const stmt of SCHEMA) _db.exec(stmt);
      for (const seed of SINGLETON_SEEDS) _db.exec(seed);
    }
    gdb.__cockpitDb = _db;
  }
  return gdb.__cockpitDb;
}

    Why sync is the right call here: SQLite is a local file — there is no network wait to overlap, and a single-tenant app has no concurrency to win. Synchronous statements make the ported handlers read almost line-for-line like their Python originals (compare the tabs in lesson 16), which mattered enormously for a parity-checked port. This is a place to resist dogma: "always async" is a rule about remote databases.

    The bundle trap — a production-only bug

    The first port of auth kept sessions in a module-level Map. Dev worked perfectly. Production failed in the strangest way: login succeeded, and the very next request was a 401.

    The cause: in a production build, each route becomes its own bundle, and a module imported by two routes is instantiated once per bundle. The Map that /api/login wrote and the Map that /api/auth/check read were two different Maps. Angular has a cousin of this bug — a "singleton" service provided again inside a lazy-loaded module — but Next's version is invisible until you build.

    Two fixes, both visible above and in server/auth.ts:

    • State that must be shared goes to globalThis (the DB handle) — one per process, bundles be damned.
    • State that must survive goes to the database — sessions live in a ts_sessions table, which also means a server restart doesn't log everyone out.

    const sse = (event, data) => `event: ${event}\ndata: ${JSON.stringify(data)}\n\n`;

function sseResponse(gen) {
  const encoder = new TextEncoder();
  const stream = new ReadableStream({
    async pull(controller) {
      const { done, value } = await gen.next();
      if (done) controller.close();
      else controller.enqueue(encoder.encode(value));
    },
  });
  return new NextResponse(stream, { headers: { "Content-Type": "text/event-stream" } });
}

    The protocol is three event types, designed so the UI can act before the prose exists: meta first (which tool ran, with its full JSON result — tables render immediately), then a stream of token events (the sentence assembles word by word), then done. Errors are an event too — a stream that has already sent 200 cannot change its status code, so in-band error events are the only honest option. That last sentence is the lesson.

    20The parity harness: porting without fear

    The port's real innovation isn't any single endpoint — it's the verification loop that made rewriting a finance backend boring. Both backends run on the same database; every request is sent to both; the answers must match. The whole method fits in five rules:

    1. Canonicalize, then diff. JSON is compared with sorted keys and floats rounded to 2 decimals — so key order and 10942 vs 10942.0 don't drown real differences. Everything else must be byte-identical: CSVs, the iCal feed, the public share pages' HTML.
    2. Write through one, read through the other. A bill toggled paid via TypeScript must show paid when Python reads it — proving both sides agree on the database contract, not just on serialization.
    3. Error shapes are part of the API. The suites assert status codes and messages — down to Python's repr() quoting in "got 'Nope'" and its list formatting in "Bills [5] are not…". Someone's frontend matches on those strings.
    4. Make the nondeterministic deterministic. The AI chat can't be byte-compared against a live model — so the harness runs a mock LLM server that both backends point at: deterministic tool picks, canned answers, scripted stream chunks. Suddenly the whole ask/stream/tools pipeline diffs like any other endpoint.
    5. Leave the database as you found it. Every suite deletes what it created and reverts what it toggled — the demo dataset survives hundreds of runs. (One suite ate a payslip once; its cleanup grew a restore step. The harness tests the harness.)

    What the diffs actually caught, a sampler: Python's str(float) everywhere ("152.0"), f"{None}" rendering as the string "None" in a report title (the port reproduces the quirk deliberately), JSZip's phantom folder entries, Starlette's RFC 5987 filenames, a missing not-a-dict validation on /preferences — found by porting the test suite and watching it fail against the new backend.
